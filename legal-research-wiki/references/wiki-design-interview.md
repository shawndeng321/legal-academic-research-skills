# 建库访谈：先问清楚要建什么样的 Wiki

新建研究库，或把已有研究库做得更深之前，先用本访谈把需求问清楚，整理成一页《Wiki 设计书》（模板 `assets/templates/wiki-design-brief.md`），经用户确认后再定 SCHEMA、目录和模板。

与写论文的五问分工：五问（`law-paper-writing` 的 `references/requirement-decomposition.md`）拆解“要写什么论文”；本访谈拆解“要建什么样的库来支撑研究”。两者可以在同一次对话中先后进行，五问的答案直接填进设计书的 A、B 两组。

## 一、提问规则

1. **一次只问 1—3 个问题**，按下面的分组顺序推进；不要一次抛出全部问题。
2. **每个问题附选项或例子**，让用户能直接选；用户的回答含糊时，给出两三个具体理解请其确认（“是 A 还是 B？”）。
3. **说明为什么问**：一句话讲清这个答案会影响库的哪部分（例如“这决定案例要不要分子目录”）。
4. **不知道就给默认方案**：用户暂时答不上来时，提出一个稳妥的默认做法并标“暂定”，继续往下问；不要卡住，也不要替用户做决定后不告诉他。
5. **不套用其他项目**：不得沿用此前任何研究库的分析框架、案例分类、标签词表或页面结构；可以把它们作为选项之一提出，但必须由用户选择。
6. **先问后建**：设计书确认前不批量摄入、不建目录。用户明确要求“先建库再说”时，只做第 D 组的材料盘点和一两份代表材料的试摄入，其余决定标“暂定”，并约定在第一个模块完成时回头补问。
7. **用用户的话记录**：设计书中的研究问题、分析框架、未来要问的问题，尽量保留用户原话，再附上代理的理解。
8. **问够就停**：必问组（A、B、C）问完，其余组按用户的回答决定是否深入；与本项目无关的组直接跳过，并在设计书中写“不适用”。

## 二、新建研究库：十组问题

### A 目的（必问）

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 这个库为谁、为什么建？ | 一篇期刊论文 / 一组系列研究 / 学位或课题的资料库 / 教学资料 / 长期积累的专题数据库 | 库的规模与完成标准 |
| 最后要产出什么？有没有时间点？ | 论文初稿、报告、案例集、比较表；投稿或结项日期 | 优先级与分批节奏 |
| 这个库是一次性的，还是要长期维护、以后继续扩充？ | 写完即止 / 持续更新 | 是否需要检修制度、版本管理 |

### B 研究问题与分析框架（必问）

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 用一两句话说，你想研究什么问题？ | “某类行政案件中，法院对某要件的认定是否随时间变化” | 研究设计页、比较页主题 |
| 你已经有分析框架或章节思路了吗？ | 有：请描述或提供思路文件 / 大致有 / 还没有 | 有则以用户框架为准；没有则先建库、在模块完成时提建议 |
| 你最想比较或解释的差异是什么？ | 不同时期 / 不同地区或法院层级 / 行政与司法 / 学说分歧 | 比较页与统计口径 |

### C 未来怎么用这个库（必问，最关键）

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| **请举 3 个你将来会问这个库的问题** | “某条款修改前后，法院认定变了吗？”“哪些案例能支持我第二节的论点？”“学界对某问题分成哪几派？” | 倒推需要哪些页面、字段和关联 |
| 写作时，你希望从库里直接拿到什么？ | 按论点排好的证据清单 / 可直接引用的案例要旨与案号 / 学术史争议地图 / 统计表 | 矩阵、比较页、争议地图是否要建 |
| 你会自己在 Obsidian 里翻，还是主要通过代理查询？ | 自己看为主 / 代理查询为主 / 两者都有 | 页面可读性要求、导航页、文件命名 |

把用户举的每个问题，在设计书中逐一对应到“由哪些页面、字段、关联来回答”；对应不上的，就是设计缺口。

### D 材料

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 手头有哪些材料？大约多少？ | 论文 PDF、案例汇编 DOCX、裁判文书、法规与司法解释、政策文件、统计数据、访谈录音、图片或扫描件 | 摄入顺序与批次 |
| 案例的来源与权威层级？ | 指导性案例、公报案例、典型案例、案例库、裁判文书网检索、检察案例 | 是否按权威层级区分 |
| 有没有你自己的作品或初稿？ | 已发表论文（可作锚点）/ 在写的初稿 / 思路文件 | 底稿页、`drafts/`、交接页 |
| 有没有目标期刊？能提供几篇范文吗？ | 期刊名；2—3 篇近期范文 | 期刊风格观察卡 |
| 以后还会持续加入新材料吗？ | 会，按什么节奏 / 基本一次到位 | 模块划分与增量关联 |

### E 深度

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 案例页要做到多细？ | 只要裁判要旨与结果 / 加争议焦点与裁判理由 / 再加裁判方法、研究定位、程序节点 | 案例模板保留哪些章节 |
| 论文页要做到多细？ | 摘要与结论 / 加核心论点与研究方法 / 再加与案例、与底稿的逐条对应 | 论文模板与关联工作量 |
| 法规要全文还是只要相关条文？ | 只要相关条文 / 相关章节 / 全文 | 法规范页粒度 |
| 需要统计吗？ | 不需要 / 简单计数 / 比率、年代切片 | 结果字段与统计口径清单 |

深度越深，每页越耗时。给用户一个大致的工作量估计（例如“100 件案例按第三档，约需分 15—20 批”），让用户权衡。

### F 组织

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 案例要不要分类？按什么分？ | 不分 / 按引用可用性（能否进脚注）/ 按权威层级 / 按争点 / 按年代 | 子目录与 `usage` 等字段 |
| 编号方式？ | 文件名带全局编号与年份（`案例N-YYYY-案名`）/ 不编号 | 文件命名 |
| 标签想按哪些维度？ | 争点、程序、责任主体、研究方法、工作用途 | SCHEMA 标签词表 |
| 需要哪些页面类型？ | 从模板清单中勾选；不需要的删去 | SCHEMA 的 type 枚举 |

### G 关联

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 最看重哪些关系？ | 论文 ↔ 案例、案例 ↔ 法规、各页 ↔ 你的底稿、论文 ↔ 论文 | 链接章节与验收重点 |
| 论文与案例怎么算“有关”？ | 只算直接引用 / 也算观点与要旨对应（主旨轨） | 关联标准 |
| 想先做哪几个比较主题？ | 列出 2—3 个争点 | 首批比较页 |

### H 时间维度（按需）

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 研究涉及的规范修改过吗？案件跨越几个规范时代吗？ | 没有 / 有，列出主要修订 | 是否启用时序版本（`references/norm-versioning.md`） |
| 你关心的是“当时怎么判”，还是“规范变化后实践变没变”，还是两者都要？ | 当时法评价 / 规范演变评价 / 两者 | 案例页时序一节与演变事件 |
| 先拿哪一个争点试点？ | 最好选一个“文本变了”的和一个“文本没变”的对照 | 试点范围 |

### I 质量与边界

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 来源核验要到什么程度？ | 逐条回读原文 / 抽查 / 先粗后精 | `source_confidence` 与 `analysis_status` 的用法 |
| 允许联网补充材料吗？ | 不允许 / 允许但要先登记 / 只限官方来源 | 材料边界 |
| 有没有保密或敏感材料？ | 未公开案件、当事人信息、未发表稿件 | 脱敏规则、哪些内容不得写回 |
| 代理可以直接改库，还是每次先给方案？ | 先给方案再改 / 小批直接改、大批先确认 | 写入权限与确认节点 |

### J 维护与协作

| 问题 | 选项或例子 | 会决定什么 |
|---|---|---|
| 多久更新或检修一次？ | 每次摄入后 / 每周 / 需要时 | 检修制度（`legal-wiki-audit-repair`） |
| 会有多个会话或多个代理同时处理这个库吗？ | 单人单会话 / 多会话 / 多代理分工 | 交接页、日志纪律、单一主写人 |
| 用什么工具？ | Obsidian 桌面端、云同步、Hermes / Claude Code / Codex | 同步与备份方式 |
| 你希望怎么汇报？ | 行动优先、简短 / 详细报告；每批多少页 | 汇报格式与批次大小 |

## 三、已有研究库：加深模式

用户要“把已有的库做得更深、加新维度”时，不从零问起。先只读查看库的现状（SCHEMA、index、log 末尾、各类页面数量与章节结构，必要时运行死链检查），再问：

| 问题 | 选项或例子 |
|---|---|
| 现在的库哪里最不好用？ | 找不到材料 / 关联太泛 / 分析层太薄 / 统计不可信 / 页面格式不一 |
| 这次想新增或加深什么？ | 新争点、新材料类型、规范时序、统计、学术史争议地图、比较层 |
| 这次加深要服务的具体问题是什么？请举 1—3 个 | 同 C 组 |
| 哪些结构不能动？ | 文件名与编号、目录、已确认的分类、正在写的论文依赖的页面 |
| 先拿哪一小块做试点？ | 一个争点、10 件左右案例、一个规范 |
| 现在是否正在写论文？ | 是：遵守“知识库与论文写作双轨隔离”，写作期间不批量改结构 |

整理成《加深方案》（同一模板，填“加深模式”部分），经用户确认后先试点，验收通过再扩展。试点中发现的既有页面错误先记录报告，确认后再改。

追加少量材料（增量摄入）既不需要重跑整套访谈，也不需要《加深方案》：读已有 SCHEMA 与设计书、盘点差量即可；只有新增维度、改变结构或涉及论文双轨时，才走访谈的“加深模式”。

## 四、访谈结束：生成设计书并确认

1. 按 `assets/templates/wiki-design-brief.md` 填写设计书，放在 `research-design/`（设计书只写建库架构结论；五问与材料进度以研究设计页为准，两处不重复维护大表）；
2. 用平实的语言向用户复述要点（一屏以内）：库的目的、未来要回答的问题、页面类型与分类、深度、首批试点；标出所有“暂定”项；
3. 用户确认后，再据此：复制并裁剪 `SCHEMA.md`（type 枚举、字段、标签词表、目录）、建目录、选用模板、确定摄入顺序与首批范围；
4. 设计书不是一次定终身：模块完成、研究问题调整或用户提出新需求时更新它，并在 `log.md` 记一条。

## 五、常见错误

- 一次抛出全部问题，或者只问一句“你想建什么样的库”；
- 没问“将来会怎么用这个库”就开始设计页面；
- 把其他项目的框架、分类、标签当成默认值直接用；
- 用户说“不知道”就停住，或者擅自决定而不标“暂定”；
- 设计书未经确认就开始批量摄入；
- 加深模式下从零重问，或者未经试点就批量改结构；
- 用户只是追加材料（如一篇论文），却重启整套访谈或重新生成设计书。
