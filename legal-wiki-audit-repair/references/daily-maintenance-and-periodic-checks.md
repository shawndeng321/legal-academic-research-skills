# 每日检修、迭代与通用巡检增强（细则）

> 由审计技能 SKILL.md 第十、十一节迁出（WIKI-12 瘦身）；触发条件与只读纪律保留在 SKILL.md。

## 一、每日检修

**触发**：用户说“今天检修”“每日检修”，或按既定计划执行。检修**默认只读（含日志）**：未获既定授权时不写任何文件，报告直接输出在会话中；发现问题按模式纪律提出方案。

**流程（约 10 分钟）**：

1. 定向：读 `log.md` 最近 30—80 行和台账最近三条执行记录；
2. 回归检查（默认全量；可信基线下可按下文启用保守增量，未覆盖项按表补查）：页面总数与台账基线对比；frontmatter 缺失与 YAML 错误为零；正式页死链为零（含畸形链接）；标签全部在 SCHEMA 词表内；类型专属字段覆盖率；论文 ↔ 案例双向对称；法规范时效（缺 效力状态/核验日期、核验过期、失效规范被引用）与案件去重（案号规范化后重复）；原始材料哈希核验（见下）；
3. 对照台账最近的 OPT，检查验收缺口和未闭环事项；
4. 日志：默认只读——拟追加的当日记录（各计数与发现）先附在报告末尾；仅在**已有既定授权**（用户明确同意过每日检修写日志，或该惯例已记入交接页／台账）时才直接追加到 `log.md`。台账只在发生实际修改时追加；
5. 发现 P1 及以上问题 → 列修复方案，等用户确认（默认每批 5—8 页）。

### 工具覆盖与补查

统一入口 `scripts/daily_check.py` 默认只读，组合本技能深检和显式指定的建库技能哈希复核；不写日志、不自动修复。技能独立安装时，不提供建库位置或缺工具会列为未检查。

```bash
AUDIT_SKILL='/实际安装位置/legal-wiki-audit-repair'
RESEARCH_SKILL='/实际安装位置/legal-research-wiki'
WIKI_PATH='/用户指定的知识库'
python3 "$AUDIT_SKILL/scripts/daily_check.py" "$WIKI_PATH" --research-skill "$RESEARCH_SKILL" --json
```

| 每日要求 | 自动覆盖 | 必须补查 |
|---|---|---|
| 定向、计数与台账基线 | 索引与磁盘页面计数 | 最近日志、台账基线与统计口径 |
| frontmatter / YAML / 死链 | 通用字段、语法、正式页链接及畸形链接 | 不可读页单列，不能算通过 |
| 标签全部合规 | FM-04 仅提示词表外且只用一次的标签 | 重复出现的词表外标签可能漏掉；全部标签与 SCHEMA 逐项核对 |
| 类型专属字段 | 通用字段及规范/案例专项 | 按 SCHEMA 补齐各类型覆盖率 |
| 论文↔案例双向对称 | 深检不覆盖；另有缺漏扫描和章节验收工具 | `scan_missing_paper_case_links.py`、`verify_case_link_sections.py` 结果结合双侧回读 |
| 法规范时效、案件去重 | 七项深检的 NORM / DUP 规则 | 回原件判断现行效力与重复归属 |
| 原件及正文指纹 | raw 下 .md 的正文及记录路径对应原件 | 缺字段、无提取物的二进制与 MANIFEST 独立指纹逐件补查 |
| OPT、分歧、日志及修复方案 | 入口列出待办，不自动关闭 | 按原流程人工核对并保持既定写入授权 |

JSON 保留工具原始结果与完整路径，`coverage` 逐项区分通过、问题、部分覆盖、未检查和人工项；`complete` 只在全部完成时才为真。退出 1 表示已知问题，退出 2 表示无已知阻断但仍有未完成项；缺依赖、运行失败、空扫描和旧版结果协议不算通过。即使所有工具正常退出，人工项未完成也不能宣称日检全部通过。来源真实性与学术内容继续按原规则核验。

每周至少运行一次全量深检：可运行 `scripts/multimodal_audit.py`，或在下述入口加 `--force-full`。`--strict` 下真实提示项计入失败，LINK-08数量观察不计入。增量机制保留到期回退，不能用连续复用推迟全量检查。

### 可选增量与失效规则

默认仍执行原有全量检查。需要复用证据时，显式指定库外基线：

```bash
# 首次全量。只有获准保存证据时才加 --save-state，父目录须存在、文件名未用过。
python3 "$AUDIT_SKILL/scripts/daily_check.py" "$WIKI_PATH" --research-skill "$RESEARCH_SKILL" --json --force-full --save-state '/库外证据目录/full.json'
# 日常只读检查；不指定 --save-state 就不创建或更新任何状态文件。
python3 "$AUDIT_SKILL/scripts/daily_check.py" "$WIKI_PATH" --research-skill "$RESEARCH_SKILL" --json --incremental --baseline '/库外证据目录/full.json'
```

- 基线只绑定七项深检。原件/正文哈希工具仍每次实查；日志台账回读、来源真实性、双向关联和学术判断继续逐项完成，不自动通过。
- 不用mtime判断未变：核对库根、完整文件路径与原字节SHA-256、检查器、Python/PyYAML版本、选项和日期。快照覆盖库内文件（Git内部目录除外）；包含链接目录、无法读取或库外配置范围时明确未完成、不保存有效基线。
- 当前增量仅支持默认页面/原件目录中的既有正式Markdown页内容变化；字段、链接图谱、素材引用和法学专项均按全库重查，复用未受影响的索引、原件摄入及日志检查。页面变空或从空变非空时一并重查索引。并非只检查改动页就忽略其入链。
- 新增、删除、移动、重命名、SCHEMA/配置/索引/日志/原件变化、自定义目录范围、损坏或旧版基线、检查器/依赖/选项变化、跨日或距上次全量达到7天，回到全量；无法界定影响范围也全量。扫描失败或期间输入变化时不保存基线，未检查项仍保留。
- JSON在 `tools.structure.result.execution` 列出实际模式、失效原因、变更文件、重查组和复用组；人类报告也显示模式。保存新的增量记录不会重置上次全量日期。状态文件的校验和用于发现损坏，不是数字签名，只使用自己保管的可信记录。
- 先在目标库测时再选择是否启用；逐文件校验指纹本身有成本，小库增量可能比直接全量慢。默认不因新增功能而切换日检方式。机器复用不代表整批验收完成，见 [最终状态验收](final-state-validation.md)。

**迭代规则**：连续检修满 3 天后，依据最近 3 天的检修记录更新检修方法（检查项增减、回归脚本改进、新易错点、口径变化），结果写入台账规则回写区（候选 → 确认），并同步 `methodology/` 中的版本说明。某天漏检时，迭代顺延至补齐连续 3 天。

**常见易错点**：

- 终审日期要取裁判结果正文中的判决或裁定日期；基本信息末项的日期常是后续事件；
- 批量修正按编号前缀定位文件，不按全名匹配；
- 结果类别的边界（和解、撤回、检察监督后重新处理、民事与行政撤销的区别）写进口径清单；判断顺序要避免包含关系导致误判（例如“不予认定”中包含“认定”二字）；
- 正则在 `re.S` 下 `.*` 会贪婪吞到文件末尾，标题行匹配用 `[^\n]*`。

## 二、通用巡检增强

- **LOG-ROTATE**：`log.md` 超过 500 条 `## [YYYY-MM-DD]` 条目时轮转：改名为 `log-YYYY.md` 存档，新建 `log.md`（保留头部说明）。
- **SHA256-DRIFT**：`raw/` 下提取文件的 frontmatter 带 `text_sha256:`（或旧字段 `sha256:`）时，按统一口径重算正文哈希比对（口径见 `legal-research-wiki` 的 `references/multimodal-pdf-extraction.md` 第 0 节；一键只读复核 `scripts/batch_extract_papers.py <raw/papers> --verify`）；或把原始文件的大小与哈希集中记录在 `raw/MANIFEST.md` 的“机器核验指纹”一节，每日检修对照重算。批量漂移（10 个以上文件同时）优先怀疑系统性原因（占位哈希、行尾符、编码、批量清洗），先归因；单个漂移核对是否真实变更，确认后更新并记入台账；**真实漂移不自动重算覆盖**。摄入新材料更新 MANIFEST 时顺手计算哈希。法学库原始材料多为 DOCX/PDF，没有哈希字段不报错。
- **CONTESTED**：列出 frontmatter 中 `contested: true` 和 `contradictions:` 的页面供用户审阅。学术分歧正是适用场景：保留双方立场、日期和来源，不静默覆盖一方；提交论文前逐页核验是否已处理。
- **CLOSED-WORLD QUERY**：查询和写作支撑只用库内内容；库内没有的如实说明并标 `[来源不明]`，提供摄入方案；空壳页面不算覆盖；联网检索属于摄入环节；来源性主张必须能回溯到库内页面与原始材料。

## 三、延伸参考

- 用户环境中若已有自己的每日检修脚本，优先使用；没有时由本技能按需执行，或把等价脚本放入 vault 的 `_scripts/`，由用户用系统定时任务（cron、launchd、Windows 任务计划程序）运行。
- 在 Google Antigravity 环境中，可使用内置的 `schedule` 工具或建议用户输入 `/schedule` 命令配置周期性自动巡检任务；发现需要用户决策的问题时，调用 `ask_question` 交付结构化确认。
- 空壳来源补全：`references/multimodal-reingest-stubs.md`（补全属于摄入动作，查询阶段禁止补全）；哈希批量修复：`references/multimodal-sha256-bulk-fix.md`。

## 四、更新技能后的自测

修改本技能（或本技能包中的任何技能）后：

1. **仓库测试**：在技能包仓库根目录运行 `python3 -m unittest discover -s tests`（兼容性、脚本安全、Bundle 更新器），全部通过才算通过；
2. **宿主加载**：Hermes 用 `hermes skills list` 确认可见、版本正确；Codex 新建任务后确认可按名称调用；DeepSeek Harness 新建会话后输入 `/legal-wiki-audit-repair` 确认技能被列出，并核对 `~/.dsh/skills/` 下三个目录为同一版本；
3. **真实知识库只读回归**：对一个真实 vault 跑全库体检，确认检查逻辑没有被改坏；
4. **小任务试跑**：用新版本执行一次每日检修等小任务，并按 `evals/pressure-tests.md` 抽测相关场景（修改了哪部分规则，就测哪部分）；
5. **闭世界验证**：审计结论全部能回溯到库内页面和原始材料。
