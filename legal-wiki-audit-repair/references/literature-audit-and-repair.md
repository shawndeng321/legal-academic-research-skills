# 文献库审计与分批修复

用于检查已有的论文实体页语料（例如 `entities/引用文献/`），再决定下一步。默认第一遍是**只读诊断**，不是批量改写。全库层面的结构与学术审计见 [systematic-vault-audit-and-optimization-ledger.md](systematic-vault-audit-and-optimization-ledger.md)；深度修复的子批次划分见 [staged-deep-repair.md](staged-deep-repair.md)。

## 一、四遍审计

1. **清单与来源**
   - 分别统计论文页、`raw/papers/` 中的 PDF、期刊范文页和 `index.md` 条目；
   - 把每个 `sources:` 值映射到实际 PDF，并确认路径存在；
   - 多出来的 PDF 先解释再报“缺失”：期刊范文 PDF 可能有意放在 `entities/范文/` 而非文献目录；
   - PDF 是不可变证据，不从 Wiki 文件名反推元数据。
2. **结构与实质**
   - 检查 YAML、标题与文件名、作者、期刊、年份、卷期、页码、DOI、标签、置信度、章节标题；
   - 检查章节**含义**而不只是字数：1,900 字的“主要结论”若其实是正文第四节，仍是错的；500 字的结论若从半句开始，仍有缺陷；
   - 摘要、核心论点、研究方法、主要结论都要能回到原文；原文没有明确方法或结论时如实说明，不编造。
3. **链接与图谱**
   - 全库（含根目录）扫描死链，区分真实死链与 SCHEMA 示例、日志历史引用；
   - 分方向统计：论文 → 底稿、底稿 → 论文、论文 ↔ 论文、论文 → 案例、案例 → 论文；
   - “引用案例”里的纯文本案名不是链接；只有映射到已存在且身份确认的案例页才算边；
   - 链接外的可读文字（如 `标题|底稿` 没有被 `[[ ]]` 包住）不是图谱边。
4. **引注精度与呈现**
   - “引用规范”区分确切的条文依据与对整部法规的背景性提及；只有原文支持时才补 `第X条`，不推断；
   - 统一条文写法（中文数字或阿拉伯数字，按 SCHEMA 选定一种），原文给出款、项时保留；
   - 检查标题后空行、关键词和 PDF 残留；
   - 全部修复后运行一次完整报告，不在只修好链接或只修好元数据时宣布完成。

### 高风险缺陷

- **元数据虚高置信**：单位、共同作者、刊名、卷期有误，却全部标 `confidence: high`；
- **结论取错章节**：取成了正文某一节，而不是结语、余论或最后实质段落；
- **结论碎片**：以“是……”“，……”等接续成分开头，即使超过字数门槛也不合格；
- **行内标题**：来源版式把“裁判理由：”“裁判要旨：”放在段落中间，解析时须先切开；
- **误报缺失来源**：原始目录里有有意分开的其他来源类别；
- **单向图谱假象**：论文页写了很多与底稿关系的文字，却没有一个真正的链接。

### 验收报告应分别列出

页数、来源数、额外或范文来源数；实质内容与章节完整性结果；核对过 PDF 的元数据缺陷；结论与方法提取缺陷；死链（误报单列）；各方向链接覆盖率；需要条文级复核的法规条目；纯格式问题；“必须修 / 建议改 / 暂缓”三类建议。

## 二、引用规范与引用案例章节

内容质量合格后，这两个章节还要做精度工作。

**引用规范**：

1. 剔除混入的非规范文本：期刊名、书名（释义、注释、逐条、探索与实践等）、论文题名（论……、……的思考等），可用关键词黑名单筛查；
2. 从 PDF 全文提取条文号：`re.findall(r'《([^》\n]{2,40})》\s*第\s*([0-9一二三四五六七八九十百]+)\s*条', text)`；同一句中并列的多个条文都要取出，不能只取第一个；
3. 中文与阿拉伯数字混写（`第14、十五、15条`）先统一换算、去重、排序，再按 SCHEMA 选定的写法输出；
4. 修复书名号嵌套错误。

**引用案例**（只从原文提取，绝不编造）：

- 案号：`[（(]\s*(\d{4})\s*[）)]\s*([^\s,，。；;]{2,15})\s*第?\s*(\d+)\s*号`；
- 指导性案例编号、检察指导性案例编号；
- 以当事人命名的案例（在原文中定位）；
- 批复、答复、复函（批复评析类论文尤其常见）。

确实没有引用案例的纯理论文章，写一行“本文未引用具体案例”，不要留空章节。子代理写“提取受限”一类说明而没有实际提取时，视为失败并重新提取。

**概念页反向链接**：概念页的“相关概念”或“相关页面”章节应列出链接到它的实体页，Obsidian 反向链接面板不能替代正文列表；批量补齐时排除自链接并去重。

## 三、分批修复

审计之后，**先取得用户对范围的明确确认**再改。第一批默认不超过 5 页，只处理来源可核实、没有歧义的缺陷；把元数据校正、语义重写和暂缓的扩充工作分开，不要一次改完整个语料。

每页修改前：

1. 重读当前页面和 PDF 相关位置（首页或结语）；
2. 记录旧字段或旧章节与有来源支持的新内容；
3. 重写结论时先写入临时文件，再只替换“主要结论”章节；没有独立结语的，注明“根据原文整理，非逐字摘录”；
4. 只更新实际修改页的 `updated`，并追加一条简短日志。

一批完成后，重读每个修改过的页面，检查 YAML 可解析、来源路径存在、必需章节齐全、结论长度与开头、无 PDF 残留、链接正常。实体目录是嵌套的，递归收集页面和链接目标。

### 工具操作中的坑

- 用顶层 `glob('*.md')` 会把嵌套目录中的有效页面误判为不存在，一律 `rglob`；
- frontmatter 补丁若在顶层键前多了一个空格，YAML 结构就变了；补丁成功后立即解析并看 diff；
- 短字符串补丁没有匹配上时，先重读实际章节再用完整行重试；不要假设文件已经改了。

## 四、向用户报告

报告要**行动优先、简短**：先说本批规模和具体页面，每页一项具体改动，列关键验收数字，最后一句说下一批（尚未开始）。用户只问“第一步是什么”或嫌回答太长时，不要重复整份审计。

用户在批准之前问“要不要改、有什么好处、具体怎么做”时，用几句平实的话加至多一张小表回答；详细内容留到批准后写进产物本身。
