# 法学研究 Wiki 排查与修复

## 技能包更新预检

每次加载本技能时，先运行 `python3 -X utf8 scripts/legal_skills_update.py check --json`（Windows 用 `py -X utf8 …` 或 `python -X utf8 …`）。脚本按 **6 小时**缓存自动检查结果；只有返回 `update_available` 时才向用户展示 `[立即更新] [查看更新说明] [稍后提醒] [忽略此版本]`，其他状态（含离线、沙箱拒绝联网或状态目录不可写）不打断当前任务并继续执行。没有用户的明确确认，绝不运行 `apply`；“查看更新说明”只读取版本、变更与本地差异，不执行写入。

**Claude Code 插件安装时跳过预检**：宿主给出的本技能基础目录路径含 `/plugins/cache/`（或位于 `.claude/plugins/` 下）时，本技能由 Claude Code 插件安装，更新由 Claude Code 负责，不运行上面的预检命令，直接执行当前任务。用户问起更新时，请其运行 `claude plugin marketplace update legal-academic-research` 与 `claude plugin update legal-academic-research@legal-academic-research`，再在会话中运行 `/reload-plugins`。若已运行预检且结果的 `update_channel` 为 `claude-plugin`，同样不运行 `apply`，只按上述方式提示。

## 运行环境（Hermes / Claude Code / Codex 通用）

- 本技能是标准 `SKILL.md` 技能目录。正文中的 `references/`、`assets/`、`scripts/` 等相对路径一律以本技能目录为基准解析；宿主加载技能时给出的基础目录就是本目录。
- 读写文件、运行命令、委派子任务均使用当前宿主自带的工具；本文不绑定任何宿主的工具名。宿主不支持子代理时，按小批次串行执行同样的步骤。
- Python 命令按系统选择：macOS/Linux 用 `python3`（macOS 默认没有 `python` 命令）；Windows 用 `py`，没有时用 `python`。本文及参考文件中写作 `python3` 的命令，在 Windows 上照此替换。所需版本为 Python 3.9 及以上。临时文件放在系统临时目录（Python `tempfile`、`$TMPDIR` 或 `%TEMP%`），不要写死 `/tmp`。
- 宿主沙箱拒绝联网或写入时，先向用户说明需要的权限；更新预检失败直接跳过。

## 概述

对法学研究 Obsidian/LLM Wiki 做全库体检、问题分级、整改设计、分批修复和复核。关注的不只是 YAML、死链和文件数量，还要判断页面是否真正支持学术研究：来源能否追溯、案例分析是否套模板、论文—案例—概念—底稿关系是否具体、群案比较层是否存在、假说是否被写成事实。

- 建库、摄入与页面规范 → `legal-research-wiki`（本技能的验收标准以它为准）；
- 研究设计页审计中的五问方法 → `law-paper-writing` 的 `references/requirement-decomposition.md`；
- 分析框架是**项目特定**的：审计时以该项目 `research-design/` 中用户确认的框架为准，不用通用模板或其他项目的框架去套。

本技能自足。宿主另有通用 Wiki 或 Obsidian 技能时可以同时使用；规则冲突时，以当前 vault 的 `SCHEMA.md`、用户本轮明确要求和原始材料为最高优先级。

## 一、先判定工作模式

严格识别用户授权，不把“排查”理解为“顺手修复”。

| 模式 | 典型表达 | 允许写入 |
|---|---|---|
| `AUDIT_ONLY` | 先不要改、只排查、只体检 | 零写入；报告直接输出在会话中；仅在用户明确要求时新建审计文件（不为留痕改日志） |
| `AUDIT_PLAN` | 排查并写整改方案、生成整改台账 | 只写用户明确指定的报告或台账；其余零写入；不改正式页面 |
| `REPAIR` | 修复、按 OPT 执行、继续优化 | 只改已确认范围；默认每批 5—8 页；授权范围内连续推进，不重复请求同类批准；新增范围／改口径／删资料时再提决策 |
| `VERIFY` | 复核、检查是否修好 | 零写入；报告直接输出在会话中；除非用户要求，不补修 |

用户只说“全面排查”时默认 `AUDIT_ONLY`。用户说“排查并修复”时，先完成审计和范围清单，再小批修复，不边扫边改。

**完成条件**：第一次写入前，能明确说出当前模式、允许写入范围和禁止写入范围。

**跨会话延续**：已确认范围、允许写入路径与未决项写入交接页（`queries/` 的 handoff 页；模板见 `legal-research-wiki` 技能的 `assets/templates/handoff.md`），后续会话据交接页继续（“继续上一批”），不重复已完成的授权确认。

## 二、定位与定向

### 2.1 确认 vault

优先使用用户本轮指定的路径；其次使用宿主的持久记忆或 `WIKI_PATH` 环境变量。不同研究项目使用独立 vault，不混扫、不混改；不因为发现旧路径就恢复、迁移或使用旧库。

### 2.2 四文件定向

依次读取：`SCHEMA.md` → `index.md` → `log.md` 最近 30—80 行 → `知识库排查修复流程与整改台账.md`（若存在；重点读任务表、规则回写区和最近三条执行记录）。缺失时记为结构问题，当前模式不允许时不擅自创建。

### 2.3 当前状态优先于历史记录

日志只说明“当时说做了什么”。必须读取真实文件、重新统计；日志与文件冲突时，以原始材料和当前文件为证据，并在报告中指出冲突。

**完成条件**：报告 vault 路径、正式分类、页面数量、原始材料数量、规范版本和最近一次变更背景。

## 三、冻结审计边界

审计前列出：正式内容目录；根目录元文件；`raw/` 原始材料目录；脚本、配置和隐藏目录；本轮是否检查 Obsidian 配置；本轮是否核对原始 PDF/DOCX 内容；本轮唯一允许写入的文件（如有）。

`raw/` 只读：原件（二进制）永不写入；提取物的正文在摄入完成后不再改，其哈希元数据字段的更新属于修复动作（先授权、备份、归因，见第八至九节与 `references/multimodal-sha256-bulk-fix.md`）。发现凭据时只报告“发现凭据”，值写成 `[REDACTED]`。

## 四、技术健康轨

所有扫描必须**递归**：正式页面通常在 `entities/引用文献/`、`entities/案例/`、`entities/法规范/` 等嵌套目录中，并包括 vault 根目录。不用顶层 `glob('*.md')` 得出全库结论。

### 4.1 目录与页面清单

统计各类页面、原始文件、空目录、根目录文件、隐藏文件和脚本；区分正式内容页、元文件（index、SCHEMA、log、台账）、0 字节幽灵页、系统文件（如 `.DS_Store`）、原始材料与中间产物。

### 4.2 YAML 与类型

递归解析 frontmatter：缺失或错误、必需字段、`type` 与 SCHEMA 和目录是否一致、`title`/一级标题/文件名的关系、`created`/`updated`、`confidence`/`contested`/`contradictions` 是否有区分作用、类型专属字段是否缺失。文件修改时间晚于 `updated` 只能列为待确认候选，不据此机械改日期。

### 4.3 来源与原始材料

- `sources:` 中的路径是否存在；非路径值是作者、目录、口述还是 Wiki 页面，不误报为“文件丢失”；
- 原始材料是否至少被一个页面引用；是否有重复哈希；
- 综合 3 个以上来源的页面是否有段落级或区块级出处；
- 是否需要 `references`、`derived_from`、`source_note`、`corpus` 等字段分流。

### 4.4 链接与 index

解析规则与 `legal-research-wiki` 共用（`scripts/wiki_links.py`，两份字节一致）。分别报告：正式内容页真实死链与缺失附件（附件按全库文件名核对，不混入笔记死链）；指向 0 字节页的“空目标”；同名歧义（同名页面不静默合并，DUP 节单列）；显式路径前缀不符；标题/块锚点不存在（块锚点待核）；畸形写法（`&#124;`、嵌套方括号、吞标题、缺右括号、空链接目标）；`SCHEMA.md` 规则示例与 `log.md` 历史链接（误报单列）、index 缺页或多余。示例和历史记录不计入死链总数；`drafts/` 中的链接（包括初稿工作版的 `[[脚注N]]` 标记）列为容忍类，单独报告、不“修复”。验收口径是“正式内容页死链为零”（`--strict` 下畸形、空目标、附件缺失、路径前缀、锚点缺失与同名歧义同为零），而不是原始总数为零；可直接运行 `legal-research-wiki` 的 `scripts/check_wikilinks.py <vault> --strict`。Obsidian 能打开 0 字节目标不代表链接健康。

**Obsidian 真实解析规则**（详见 `legal-research-wiki` 的 `references/linking-and-cross-references.md`）：

- 别名分隔先按 `\|` 再按 `|` 拆：`re.split(r'\\\||(?<!\\)\|', raw)[0]`；
- `&#124;` 不是分隔符，出现处按死链计并列为 P1；
- 反引号内的示例链接也会被图谱解析；维护文档中的示例一律写纯文本，包括自己新追加的日志条目；
- Graph View 空白节点排查 = 全库未解析链接扫描，文件列表干净不等于图谱干净；
- **畸形链接**：缺右括号的 `[[目标]`（用宽容正则 `\[\[([^\]\n]{2,200})\]` 并检查其后字符不是 `]`）、吞掉下一行标题的 `[[目标## …`、嵌套 `[[[[`/`]]]]`；
- **幽灵文件复活**：删除 `…&.md` 等 0 字节幽灵文件后，`.obsidian/workspace.json` 的 `lastOpenFiles` 仍会在下次启动时重建它们。清理时：①从 workspace.json 剥离相关路径并复查（首轮可能漏）；②在 `app.json` 的 `userIgnoreFilters` 中加入 `.maintenance`、`ghosts`；③请用户完全退出 Obsidian 再打开；
- 检查文件存在时带 `.md` 后缀，裸名永远不存在；
- 案号匹配用完整案号并同时处理全角、半角括号。

### 4.5 图谱与孤岛

入站关系分两种统计：导航入站（来自 index）与实质入站（来自其他正式内容页）。index 可达不等于知识上相关。计算分类间边矩阵、各类出入站分布、孤岛和中心节点；检查是否为大量页面指向少数中心的星形结构。不为降低孤岛数而机械补链接；每条关系要能说明呼应、补充、分歧、规范要件、证明结构、程序阶段或时间演变。

### 4.6 标签、命名和格式

标签是否都在 SCHEMA 词表中；是否混用主题、要件、程序、来源、结果和研究用途；同义标签、层级缺失、自由标签扩散；重复 stem、重复 title、空格和异常标点；标题前后空行；PDF 残留、关键词换行、中文摘要夹英文；结论长度与碎片开头。超过 200 行的页面只列为可读性候选，不机械拆分。论文页一次运行完整六维检查（摘要、结论、PDF 残留、关键词、YAML、标题空行），不修一项就宣布全库通过。

### 4.7 脚本与 Obsidian 配置

审计生成脚本是否有：绝对路径、过期输出目录、`open(..., 'w')` 直接覆盖、无 `--dry-run`/不覆盖保护/备份/映射清单、固定的概念或案例分析模板、只验证文件存在不验证内容。存在即标 P1，禁止直接运行；修复后先输出到临时目录，用 1—2 个样本验证。

检查 `.obsidian/graph.json`、`app.json`、核心插件和新笔记默认位置。研究视图与质检视图分开：研究视图隐藏未解析链接和孤岛并按目录着色；质检视图显示孤岛、未解析链接和方向箭头。

### 4.8 研究设计与统计状态

- “统计口径可执行”不等于“已经计算”：核查数字是否真的算过、是否基于逐案文本归类、结果是否写入矩阵并更新了研究假说状态；绝不编造数字；
- 结果字段落地后，机器全量重算与人工口径交叉核对，差异逐项归因，不直接改定稿数字；
- `methodology/` 页若注明“与某技能某版本同步”，技能升级后同步其版本说明与新增规则。

**技术轨完成条件**：给出可复算的计数、具体路径和误报分类，而不是“结构良好”。

## 五、学术可用性轨

技术合格不代表学术可用。页面可能很长、有来源、无死链，却因模板化分析或无证据结论而误导研究。

### 5.1 分类抽样

每个主要类别至少抽查两页：一页结构完整、内容具体的基准页；一页最短、最长、链接异常、重复度高或分类可疑的离群页。通常覆盖研究设计、概念、引用文献、范文、底稿、案例、比较页。空类别本身作为结构发现记录。

### 5.2 案例页

区分原始事实、程序历程、裁判结果/理由/要旨、Wiki 研究分析四层。检查争议焦点是否与裁判理由一致，基本案情与程序历程是否重复，研究定位是否引用本案具体事实、条文或证明结构，相关论文和案例是否真有具体关系。

### 5.3 论文页与论文—案例关系

检查摘要、核心论点、研究方法、主要结论、引用规范、引用案例、与底稿和其他论文的关系、相关概念。

- 论文—案例的“引用”关系必须有案名、案号、指导案例号或唯一事实支持；主题相似不构成引用；
- “主旨”关系：案例要旨与论文核心论点之间的印证、支撑或反衬，每条要写理由；泛泛“相关”的链接是缺陷，不是网络；
- 双向对称：论文 → 案例与案例 → 论文的条目数一致，逐对校验；
- 早期批量生成的纯链接**默认不可信**，按 `references/batch-operations.md` 第六节逐条核验：有联系补理由，无联系删除；用户无法逐条确认时，由 AI 按标准程序化核验并列出保留、删除及理由；
- 案例页不应同时存在“与论文的关联”和旧的“相关论文”两个章节：核验后合并。

### 5.4 概念页

至少应有定义、当前认识、代表文献、代表案例、争议或反方、规范依据、相关概念。只有作者名而无论文链接，或声称“法院已形成趋势”却无案例证据，属于可追溯性缺口。

### 5.5 研究设计与比较页

未摄入的样本、未统计的数据和待核口径必须写成假说或待核状态。比较页须有样本纳入标准、比较表、相同点、差异点、反例与边界（须检查；暂未找到时以检索范围与结论限制如实说明）、可支持的论文主张（格式见 `references/comparison-page-format.md`）。

### 5.6 模块完成后的薄弱检查

- 概念页：只有定义无案例或论文支撑；代表案例未链接；未引用相关规范；
- 比较页：新摄入案例是否符合纳入标准却未补入；差异点表格链接写法错误；“可支持的论文主张”未随网络更新；
- 案例库很大而论文只用少量案例时，考虑增加 `usage` 标记（详析、脚注、统计、不用），大规模打标前先报方案。

**学术轨完成条件**：每个系统性问题至少有“机器统计证据 + 人工抽样证据”；不能只凭重复计数断言内容错误，也不能只凭一页推断全库。

## 六、模板化与假性图谱检测

1. 提取同名章节，去除空白、日期、数字和链接目标后计算归一化指纹；
2. 统计重复长段落和重复链接组合；
3. 比较“基本案情”与“程序历程”的包含关系和相似度；
4. 找出几十页共用的争议焦点、裁判方法、研究定位和跨案关系；
5. 选最大重复组中的一页回读原始材料；
6. 与一页高质量基准对照，确认模板是否造成错配。

重复只是风险信号，只有原始材料和页面语义能证明“错误”。确认模板错配后，冻结相关分析层，不再用它生成比较页或论文统计。

## 七、问题分级

| 等级 | 定义 | 例子 |
|---|---|---|
| P0 | 数据或解析灾难 | 原始材料被改、批量覆盖、YAML 全库损坏、正式内容大量丢失 |
| P1 | 会误导研究或继续造成破坏 | 错误争点、模板化案例分析、脚本直接覆盖、无来源裁判结论、`&#124;` 死链 |
| P2 | 结构和可追溯性不足 | SCHEMA 类型不一致、来源语义混用、真实孤岛、缺比较层、标签失控 |
| P3 | 展示和低风险一致性 | 空行、文件命名、Graph 颜色、系统文件、日期候选 |

每项发现包括：编号、证据、影响范围、风险、修复方法、首批页面、验收条件、是否需要用户判断。

## 八、整改台账协议

根目录已有 `知识库排查修复流程与整改台账.md`（或旧名 `优化log.md`）时：先读取，不覆盖；复核旧基线是否仍成立；更新任务状态或追加“复核/纠正”；每次执行在末尾追加记录；规则迭代先登记为候选，不直接写成已确认规则。执行记录的 OPT 编号与任务表核对，错位时保留历史原文并补澄清说明。

不存在时：`AUDIT_ONLY` 不擅自创建；只有用户明确要求才创建；它是根目录元文件，不计入正式页数或 index（除非 SCHEMA 另有规定）。

台账至少包含：使用规则；基线计数和已通过项目；分类抽样；P0—P3 编号任务；OPT 任务状态总表；分阶段执行顺序；全局验收清单；待处理页面清单；规则回写区（候选/已确认）；追加式执行记录模板。

修复后两处都写；只读审计与默认状态的每日检修中不为“留痕”修改 `log.md`（检修的既定授权例外见第十节）。

## 九、分批修复

用户允许修复后，一次只处理一个 OPT 任务：

1. **冻结范围**：列出 5—8 个页面、原始材料、旧内容和预期修改；超过 10 页先确认；
2. **回读来源**：事实、观点、法条、程序节点和映射都要有原材料支持；
3. **外科式修改**：只替换目标字段或章节，不重建整页，不碰 `raw/`；
4. **关系复核**：新链接目标存在、有实质内容、关系具体，必要时双向；
5. **日期与日志**：只更新实际改动页的 `updated`；台账追加详细记录，log 追加简记；
6. **全量验收**：复跑 YAML、来源、死链、空壳、格式和相关图谱检查；
7. **抽样回读**：逐页读回修改段落，不只相信补丁成功或子代理自报完成。

- 修案例页时只重写有证据问题的研究分析层，保留可核验的原始事实；证据不足写“暂不形成跨案结论”，不用通用模板填满；
- 修概念页时，代表案例和论文必须支持明确命题，不为凑链接添加；
- 修论文页时，元数据以 PDF 首页或可靠书目来源为准，结论必须读 PDF 末尾确认；
- 法规范库尚未完整摄入前，只列“需摄入的规范和条文范围”，不系统补条文号。

**连续推进与跨会话延续**：范围与批次预算已确认时，同类修改连续执行（默认每批 5—8 页），不逐项请求批准；新增范围、改统计口径、删除资料时单独提出决策。已确认范围、允许写入路径与未决项写入交接页，后续会话据此继续（“继续上一批”）。

### 9.1 批量操作

重命名、重编号、链接迁移、反向链接补齐、批量填充、论文—案例同步、规范依据小节插入、YAML 字段批量插入：完整流程、脚本和事故教训见 `references/batch-operations.md`，脚本在 `scripts/`。核心纪律：

1. 映射和备份存 `.maintenance/<任务>-<日期>/`，不只放临时目录；
2. old == new 的同名项只改内容，绝不删除；
3. 中文文件名用正则取编号，不用字符切片；
4. 重命名后全库替换全部链接写法；移动目录不需要改链接；
5. 批量补反向链接排除自链接、去重、章节边界正确；
6. 表格内别名链接用 `\|`；
7. 写入前先试运行；并行编辑时编号以写入时的文件为准；
8. 验收：死链为零、错误模式残留为零、单向链接为零、编号连续。

群案统计提取见 `references/group-case-stats-extraction.md`。

## 十、每日检修与迭代

**触发**：用户说“今天检修”“每日检修”，或按既定计划执行。检修**默认只读（含日志）**：未获既定授权时不写任何文件，报告直接输出在会话中；发现问题按模式纪律提出方案。

**流程（约 10 分钟）**：

1. 定向：读 `log.md` 最近 30—80 行和台账最近三条执行记录；
2. 全库回归（一个脚本扫完）：页面总数与台账基线对比；frontmatter 缺失与 YAML 错误为零；正式页死链为零（含畸形链接）；标签全部在 SCHEMA 词表内；类型专属字段覆盖率；论文 ↔ 案例双向对称；法规范时效（缺 效力状态/核验日期、核验过期、失效规范被引用）与案件去重（案号规范化后重复）；原始材料哈希核验（见下）；
3. 对照台账最近的 OPT，检查验收缺口和未闭环事项；
4. 日志：默认只读——拟追加的当日记录（各计数与发现）先附在报告末尾；仅在**已有既定授权**（用户明确同意过每日检修写日志，或该惯例已记入交接页／台账）时才直接追加到 `log.md`。台账只在发生实际修改时追加；
5. 发现 P1 及以上问题 → 列修复方案，等用户确认（默认每批 5—8 页）。

每周至少运行一次深检脚本 `scripts/multimodal_audit.py`（加 `--strict` 时提示项也计入失败）：它能抓到轻量检修漏掉的畸形链接、空目标（0 字节页面）与同名歧义。

**迭代规则**：连续检修满 3 天后，依据最近 3 天的检修记录更新检修方法（检查项增减、回归脚本改进、新易错点、口径变化），结果写入台账规则回写区（候选 → 确认），并同步 `methodology/` 中的版本说明。某天漏检时，迭代顺延至补齐连续 3 天。

**常见易错点**：

- 终审日期要取裁判结果正文中的判决或裁定日期；基本信息末项的日期常是后续事件；
- 批量修正按编号前缀定位文件，不按全名匹配；
- 结果类别的边界（和解、撤回、检察监督后重新处理、民事与行政撤销的区别）写进口径清单；判断顺序要避免包含关系导致误判（例如“不予认定”中包含“认定”二字）；
- 正则在 `re.S` 下 `.*` 会贪婪吞到文件末尾，标题行匹配用 `[^\n]*`。

## 十一、通用巡检增强

- **LOG-ROTATE**：`log.md` 超过 500 条 `## [YYYY-MM-DD]` 条目时轮转：改名为 `log-YYYY.md` 存档，新建 `log.md`（保留头部说明）。
- **SHA256-DRIFT**：`raw/` 下提取文件的 frontmatter 带 `text_sha256:`（或旧字段 `sha256:`）时，按统一口径重算正文哈希比对（口径见 `legal-research-wiki` 的 `references/multimodal-pdf-extraction.md` 第 0 节；一键只读复核 `scripts/batch_extract_papers.py <raw/papers> --verify`）；或把原始文件的大小与哈希集中记录在 `raw/MANIFEST.md` 的“机器核验指纹”一节，每日检修对照重算。批量漂移（10 个以上文件同时）优先怀疑系统性原因（占位哈希、行尾符、编码、批量清洗），先归因；单个漂移核对是否真实变更，确认后更新并记入台账；**真实漂移不自动重算覆盖**。摄入新材料更新 MANIFEST 时顺手计算哈希。法学库原始材料多为 DOCX/PDF，没有哈希字段不报错。
- **CONTESTED**：列出 frontmatter 中 `contested: true` 和 `contradictions:` 的页面供用户审阅。学术分歧正是适用场景：保留双方立场、日期和来源，不静默覆盖一方；提交论文前逐页核验是否已处理。
- **CLOSED-WORLD QUERY**：查询和写作支撑只用库内内容；库内没有的如实说明并标 `[来源不明]`，提供摄入方案；空壳页面不算覆盖；联网检索属于摄入环节；来源性主张必须能回溯到库内页面与原始材料。

**脚本**：

- `scripts/multimodal_audit.py "<WIKI_PATH>" [--json] [--strict] [--privacy]`：七项全库深检——索引一致性、未摄入原始材料、frontmatter 质量、链接完整性、文件卫生与惯例、日志格式、法学专项（法规范时效、案件去重、隐私格式）。中文报告，每条发现含规则编号（IDX/RAW/FM/LINK/HYG/LOG/NORM/DUP/PRIV）、路径、定位、严重程度与检查范围；退出码 0=通过、1=存在阻断项（`--strict` 下提示项也计入）、2=执行失败或扫描不完整，未扫描到对象时不输出“通过”。需要 PyYAML（见 `requirements-dev.txt`）；链接解析与 `legal-research-wiki` 的 `check_wikilinks.py` 共用 `scripts/wiki_links.py`（两份字节一致）。已按法学库适配：页面以 vault 相对路径为身份、同名文件单独报告；默认扫描整个 `raw/`（含 `cases/`、`法规范/`），仅 `raw/transcripts`、`raw/screenshots` 强制同名提取；frontmatter 用真实 YAML 解析并检查字段类型、空值与重复键（解析失败单列）；标签词表兼容分类标题式 SCHEMA，只对单次使用且不在词表中的标签提示；跳过 `.maintenance`、`drafts`、`_scripts`、备份与隐藏目录（备份不得掩盖死链）；正式目录、排除目录、必填字段、`norm_verify_max_age_days` 与 `privacy{enabled, extra_patterns}` 可用 vault 根的 `wiki-audit.config.json` 覆盖（`--privacy` 启用可选隐私检查，命中值打码、只报告不改动）。不要用上游 multimodal-wiki 的脚本覆盖。
- 用户环境中若已有自己的每日检修脚本，优先使用；没有时由本技能按需执行，或把等价脚本放入 vault 的 `_scripts/`，由用户用系统定时任务（cron、launchd、Windows 任务计划程序）运行。
- 空壳来源补全：`references/multimodal-reingest-stubs.md`（补全属于摄入动作，查询阶段禁止补全）；哈希批量修复：`references/multimodal-sha256-bulk-fix.md`。

## 十二、全量验收标准

每个修复批次都报告：

- [ ] YAML 错误为零；
- [ ] 实际原始路径缺失为零；
- [ ] 正式内容死链为零，示例和历史链接单列；
- [ ] 新页面有实质内容，空壳与空章节为零；
- [ ] 修改页 `updated` 正确；
- [ ] 新链接关系具体，必要时双向；
- [ ] 案例事实、裁判理由和研究分析明确区分；
- [ ] 未核数据没有被写成事实；
- [ ] index 计数和分类正确；
- [ ] 台账与全局日志记录完整；
- [ ] 用户要求的所有维度同时复核，而不是只验一项。

全部适用项通过才能说“本批完成”；仍有问题时写出剩余计数和页面，不用“总体没问题”掩盖。

## 十三、常见陷阱

1. 排查时顺手修改；
2. 把 index 链接算作学术关系；
3. 把长页面当成高质量页面；
4. 用主题相似代替引用证据；
5. 只扫子目录，漏掉根目录幽灵页和嵌套实体；
6. 把非路径的 source 误报为文件缺失；
7. 机械消灭孤岛，制造假性稠密网络；
8. 看到重复段落就判错，而不回读原材料；
9. 信任旧日志或子代理的自我报告；
10. 修一项就宣布全库完成；
11. 直接运行旧生成脚本；
12. 未经确认批量修改（默认 5—8 页，超过 10 页先列清单确认）。

## 十四、向用户报告

行动优先，不先堆技术细节：

1. 本次模式与写入范围；
2. 已通过的项目；
3. 最严重的 3—5 个问题及具体证据；
4. 分类结构是否需要推倒重来；
5. 第一批建议处理的页面和原因；
6. 文件位置；
7. 验收计数和明确未处理的事项。

用户只问“下一步是什么”时，只回答第一批范围、每页一项修改和验收标准，不重复整份审计。

## 十五、更新技能后的自测

修改本技能（或本技能包中的任何技能）后：

1. **仓库测试**：在技能包仓库根目录运行 `python3 -m unittest discover -s tests`（兼容性、脚本安全、Bundle 更新器），全部通过才算通过；
2. **宿主加载**：Hermes 用 `hermes skills list` 确认可见、版本正确；Claude Code 新建会话后确认技能出现在可用技能中（插件安装的运行 `/reload-plugins`）；Codex 新建任务后确认可按名称调用；
3. **真实知识库只读回归**：对一个真实 vault 跑全库体检，确认检查逻辑没有被改坏；
4. **小任务试跑**：用新版本执行一次每日检修等小任务，并按 `evals/pressure-tests.md` 抽测相关场景（修改了哪部分规则，就测哪部分）；
5. **闭世界验证**：审计结论全部能回溯到库内页面和原始材料。
